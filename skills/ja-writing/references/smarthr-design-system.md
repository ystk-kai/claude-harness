## まず押さえる

1. **位置づけは「指針」であって強制規則ではない**。原典自身が「絶対に守らないといけない規則ではありません」と明言し、わかりやすさを都度確認する姿勢を求める。適用範囲はアプリだけでなくヘルプセンター等、ユーザーが触れるもの全部。重視する観点は一貫性・統一感・検索性・標準化・効率化の 5 つで、「日本語スタイルガイド 第3版」を参考にしたと書く (C/index.mdx, C/how-to-use.mdx)。

2. **構成は 5 つ**: 基本的な考え方 (writing-style)・用字用語 (idiomatic-usage)・UI テキスト・ヘルプページ・リリースノート。原典が明示する依存は「用字用語や UI テキストなどの具体的なガイドラインは基本的な考え方に基づく」だけ。エラーメッセージ・ステータスラベル・通知メール等は「基本的な考え方と用字用語に準拠」、ヘルプページとリリースノートは「基本的な考え方・用字用語・UI テキストに準拠」と宣言する。ただしヘルプページは「ユーザーのメンタルモデルに配慮して特例を設けている」と明記しており、実際に basic-rule は英数字・記号を半角とする (記号ページの全角原則と異なる) (C/how-to-use.mdx, C/error-messages/index.mdx, C/help-center/index.mdx, C/help-center/basic-rule.mdx, C/release-note/releasenotes.mdx)。

3. **文体の原則 (writing-style) は 9 項目**: 冗長表現を避ける (「〜することができる」「〜を行う」型)、文法的に正しい表現 (例は「ご参考ください」)、常用漢字表の表外読みを避ける、読みやすい語はひらがなに開く (ただし開きすぎない)、カタカナ語はまず漢字語への言い換えを検討、敬語を盛りすぎない、同じものを複数の言い方で呼ばない、格助詞を省略しない、社内用語・専門用語を避ける。9 項目中 7 項目に出典 (文化庁の常用漢字表など) か議事録リンクが付き、「同じことを複数の表現で説明しない」と「格助詞を省略しない」の 2 項目には無い (C/writing-style.mdx)。

4. **用字用語は「索引 + 8 カテゴリの詳細ページ」**。カテゴリは漢字とひらがな・カタカナ語・記号・数字と数え・操作を表す用語・コンポーネントの呼び方・SmartHR の用語・その他類似語の使い分け。索引 (ichiran) は推奨表記の 50 音順で「推奨 / 非推奨 / 詳細ページへのアンカー」の 3 列。**表記ゆれで迷ったら索引から引き、詳細ページで理由を読む**のが原典の推奨動線 (C/idiomatic-usage/ichiran.mdx, C/how-to-use.mdx)。

5. **かな・漢字の判断軸は「読解負荷」**。送りがなは内閣告示「送り仮名の付け方」に従う (固有の書類名は正式名称優先)。個別語の開く / 閉じるは語ごとに理由付きで決めており、「漢字のほうがひと目で意味が取れる」場合は漢字側に倒す例もある (C/idiomatic-usage/hiragana.mdx)。

6. **カタカナ語の長音は英語の語尾で決める**: -er / -or / -ar は長音あり、-y は長音なし、例外語は個別列挙。wi/we/wo は「ウィ/ウェ/ウォ」に統一 (NHK の調査を出典に付ける)。英字略語や俗な略し方 (PC・スマホ型) を避けて馴染みのあるカタカナ語に統一する規則もここ (C/idiomatic-usage/katakana.mdx)。

7. **記号は「全角が基本、前後にスペースを入れない」**。例外として半角を使う場面 (英数字に付く記号、桁区切り、階層区切り、変数の波括弧など) と、「？」「！」の後に文が続くときだけ全角スペースを入れる規則がある。和欧混植で英単語・数字の前後に半角スペースを入れない。括弧は種類ごとに用途が割り当てられており (補足・入力値や強調・UI 上の項目名やボタン名・ユーザー命名のオブジェクト名・変数・コード)、二重かぎ括弧と引用符は使わない。見出しと単語の箇条書きでは句点を省く。列挙は順序に意味があれば読点、無ければナカグロ (C/idiomatic-usage/symbol.mdx)。

8. **数字と数え**: 算用数字の半角が基本で、熟語・慣用句は漢数字 (「数字を入れ替えて不自然なら漢数字」という判定法付き)。丸数字は環境依存文字として原則不可。従業員は「名」、アカウントや書類は「件」。日付は表示言語ごとの形式 (UI では SmartHR UI の日付フォーマッタに任せる)、時刻は 24 時間制、期間は波線、3 桁カンマ、ファイルサイズは英字 2 文字単位 (C/idiomatic-usage/count.mdx)。

9. **操作語は UI 部品ごとに動詞を固定する**: ボタンは「押す」、テキストリンクは「開く」、ラジオは「選択する」、チェックボックスは「チェックを入れる / 外す」、スイッチは「有効にする / 無効にする」。「クリック」「タップ」は使わない。止める系 (キャンセル / 取り消し / 中断) と戻す系 (解除 / 差し戻し / 戻す) は意味の違いで使い分ける。外来語の操作名は語ごとに判断し、インポート・エクスポート等は和語側に寄せる一方でアップロード・ダウンロードはそのまま使う (C/idiomatic-usage/action.mdx)。

10. **UI テキストは品詞で書き分ける**: 説明文は敬体で動詞まで書き体言止めを避ける。画面タイトル・項目名は名詞 (助詞は「の」)。ボタンは動詞の終止形だがサ変動詞の「する」は省く (オブジェクトを付けるなら助詞は「を」)。ダイアログのタイトルと実行ボタンのアクションを一致させる。リンクは「こちら」を避けて移動先を想起できる文言にする (WCAG 2.4.4 を参考文献に付ける)。監査ログだけは検索性を優先し、完結文ではなく「目的語 + を + 動詞」型の体言止めに統一する (C/ui-text/app-writing.mdx)。

11. **エラーメッセージは「事象・原因・対処」の 3 要素**。目的は「ユーザーがメッセージを見て問題を解決でき、次の操作に進める」こと。全部を載せられないときは**原因 > 対処 > 事象**の優先順。表示スペースで要素を変える: NotificationBar は原因 (または原因 + 対処) を 1 文程度、バックグラウンド処理は結果概要に事象・エラー詳細に原因と対処を書き、両者に同じ文を繰り返さない。原因の型 (仕様上不可・制限値超過・既に済・存在しない・未入力・未選択・不正・不一致・権限なし・不明) ごとに `{{変数}}` 入りの文型テンプレートがある (C/error-messages/overview.mdx, notificationbar.mdx, background-process.mdx)。

12. **ヘルプページは 5 タイプ** (機能概要・操作手順・仕様の一覧・トラブルシューティング / FAQ・用語) に分け、タイプごとに構成要素の順番と書き方を定める。共通の書き方 (basic-rule) は自己レビュー用チェックリスト形式で、「取捨選択・配置・正確かつ簡潔・表記ルール・スクリーンショット」の 5 群。曖昧さを生む表現 (主観の入った言い方、複数の読み方ができる助詞、例外をほのめかす副詞、曖昧な指示語、注意事項の括弧書き) を避ける項目が具体的 (C/help-center/index.mdx, C/help-center/basic-rule.mdx)。

13. **リリースノートは「ユーザーができるようになったこと / できなくなったこと」を書く**。コードの変更ではなくユーザー視点の変化と背景を伝える。カテゴリは 6 つ (新機能・改善・アクセシビリティ向上・不具合修正・廃止した機能・その他の変更)。見出しは 20 文字程度で句点なし、画面上の変更ではなく得られる価値を書く。本文は「アプリ上の変更点 / リリースの背景 / ユーザーにとって変わったこと」の 3 要素。文言変更のうちどれを「アクセシビリティ向上」に分類するかの基準ページが別にある (C/release-note/releasenotes-purpose.mdx, releasenotes.mdx, text-check-list.mdx)。

14. **ai/ は「AI で文章を書く方法」ではなく「AI 機能についての書き方」**。規定は 2 つだけ: (a) AI 機能の命名 — 個別機能は「AI + 目的 + 機能」型で、ロボットや人の役割を想起させる名前は使わない (UI 上は名前ではなく「by AI」ラベルで示す)。AI が中心価値の新規アプリは逆に役割を想起させる名前を許す。(b) AI 機能のヘルプページ — 学習利用の有無を明記する、品質と動作の期待値を合わせる注意書きを類似機能間で同じ表現にそろえる、有効化が同意とみなされる機能には注意書きを置く (C/ai/index.mdx, ai-name.mdx, ai-help.mdx)。

15. **textlint との関係は「この repo 自身の MDX を lint している」まで**。ガイドライン本文は textlint-rule-preset-smarthr に言及していない。repo の `package.json` が `textlint-rule-preset-smarthr` (^1.38.2) と `textlint-rule-prh` を devDependency に持ち、`.textlintrc` で preset の一部ルール (句点混在・文長・全角半角間スペース・括弧周りスペース) を無効化し、`dict/prh-books.yml` (蒸留時点では中身はコメントアウトのみ) を読む。ガイドライン本文中の NG 例は `{/* textlint-disable */}` コメントで lint から除外している。各ガイドライン規則と preset のルールの対応表は原典に無い (AGENTS.md, package.json, .textlintrc)。

## 出典 / 議事録の辿り方

- 各規則は `## 規則名` の直前に `{<span id="..." />}` で英語スラッグのアンカーを持ち、索引や他ページからは `/products/contents/<dir>/<page>/#<id>` で参照される。repo 内では `src/content/articles/products/contents/<dir>/<page>.mdx` を grep すればアンカー位置に着く。
- 規則の下位見出しは `### 説明` → (`### 例` / `### 例外` / `### 注意点`) → `### 出典` または `### 議事録`。
  - **出典**: 公開資料 (文化庁の常用漢字表・内閣告示「送り仮名の付け方」、NHK 放送文化研究所の調査、WCAG 解説、日本語スタイルガイド第3版、書籍など)。外部から確認できる。
  - **議事録**: 社内 Slack (`kufuinc.slack.com`) や Notion の URL。**外部からは開けない**ので、決定理由は `### 説明` の本文から読むしかない。議事録 URL の代わりに理由を地の文で書いている項目もある (C/ui-text/app-writing.mdx の一覧の項)。
- 出典も議事録も無い規則がある (語の呼称統一の一部など)。根拠の強さは規則ごとに異なる。
