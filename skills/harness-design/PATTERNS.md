# harness-design: 採録した転用可能な手法

原典 clone を持たない資料 (探索索引の先、記事、製品リポジトリ等) から採った、**ハーネス設計に転用できる手法だけ**を置く。
資料の索引ではないので 1 項目 = 1 手法 + 出所 1 行。

蒸留版 (`references/*.md`) との役割分担:

- **蒸留版** = 「その原典に何が書いてあるか」の地図。継続参照する資料に 1 ファイル
- **このファイル** = 「他所で見た手法のうち、蒸留版のどれにも無くて使えるもの」の置き場。資料本体は追わない

## 採録ゲート (5 つ全て満たすものだけ書く)

1. **既存の蒸留版と被らない** — 採録前に `rg -i '<キーワード>' references/*.md` で確認する。被ったら採録しない。
   既存に上位互換があるなら既存が正 (部分集合を二重に持たない)
2. **実際に読んで確認した** — 推測や「要約の要約」で書かない (DISTILLING.md と同じ規律)
3. **転用可能** — 特定製品の使い方でなく、他のハーネスに持ち込める手法として書けること
4. **出所が 1 行で書ける** — URL + 確認したファイルパス。数値を引くなら撤回の有無まで確認する
5. **原典 clone を足すほどではない** — 資料全体に継続参照の価値があるなら、ここではなく蒸留版を作る
   (手順は [../claude-harness-refs-update/DISTILLING.md](../claude-harness-refs-update/DISTILLING.md) の「新規リポジトリの追加」)

## 退出規約

- 公式資料や蒸留版に同等以上の記述が現れたら、この項目を**削除して蒸留版側に寄せる** (ゲート 1 の裏返し)
- 出所が消えた・撤回された手法は削除する
- ここの項目は二次情報。公式一次資料と食い違ったら公式が正 (優先順位は SKILL.md の規則に従う)

## 手法

### 1. 抑制系の介入には非交渉領域を明示列挙する。ただし列挙だけでは漏れる

ハーネス介入には capability を**足す**側と、over-engineering や冗長さを**抑える**側がある。
抑える側の介入は、抑えてはいけないものまで抑える固有のリスクを持つ。
そのため抑制系の指示には「絶対に削らない領域」を本文に列挙する
(実例の 5 項目: 信頼境界での入力検証 / データ損失を防ぐエラー処理 / セキュリティ / アクセシビリティ / 明示的に要求されたもの)。

重要なのは、**列挙しても漏れるという実測がある**こと。第三者ベンチは「correctness と security の退行は無し」としつつ
「24 タスク中 5 件で日常的な不正入力処理が削られた」と報告している。
つまり非交渉領域の明示は必要条件で、十分条件ではない。抑制系を入れるなら項目 4 の実測とセットで運用する。

出所: `DietrichGebert/ponytail` の `skills/ponytail/SKILL.md` "When NOT to be lazy" 節、
実測は同 `benchmarks/README.md` の "Independent benchmarks" 欄 (KuldeepB19、24 タスク・480 builds)

### 2. 常時有効を狙う指示には persistence 節と解除条件を書く

「毎回こう振る舞え」系の指示は、ターンが進むと元の挙動に戻る (drift する)。
対策として指示本文に persistence を明文化する。実例の構成は 4 点:

- 毎応答で有効であること
- **迷ったら有効側に倒す** (曖昧なときの既定を指示側で決めておく)
- 解除する語をリテラルで限定列挙する (それ以外では解除しない)
- 既定の強度と切り替え方法

解除条件を書くことが要点。書かないと、ユーザーの何気ない一言が解除と解釈される余地が残る。

**先に上位の機構を検討する**: 同じ drift に対して、指示ではなく**スクリプトの制御フローで強制する**方が強い
(`references/claude-cookbooks.md` の「まず押さえる」16 — "Double-check your findings" は指示にすぎず
context 圧のもとで飛ぶが、制御フローなら飛ばない)。コードで表現できる場面ではそちらを使う。
この項目が効くのは、プロンプトや常時ルールしか手段が無い層 (skill 本文・CLAUDE.md・ホスト側の rule ファイル) に限る。

出所: `DietrichGebert/ponytail` の `skills/ponytail/SKILL.md` "Persistence" 節

### 3. 度合い (強度) の指定は、同一入力に対する複数出力の例で定義する

「簡潔に」「最小限に」のような度合い語は、語だけでは共有されない。
複数の強度を用意するなら、**同じ入力 1 つに対して各強度の出力を並べて見せる**のが最も曖昧さが少ない。

実例は 3 段階 (控えめ / 既定 / 極端) に対し、「API レスポンスにキャッシュを追加して」という 1 入力で、
控えめ = 依頼どおり実装し、より軽い代替を 1 行添えるだけ / 既定 = 標準ライブラリの 1 行で済ませ、省いたものと追加条件を明示 /
極端 = プロファイラが要ると言うまで作らない、と 3 つの出力を並記している。
表で「何が変わるか」を書くだけでは足りず、出力例が判断を確定させている。

出所: `DietrichGebert/ponytail` の `skills/ponytail/SKILL.md` "Intensity" 節

### 4. ハーネス介入の効果を単発プロンプトで測ると過大に出る

介入の前後を「1 プロンプト → 1 完了」で比べると効果が過大に出る。理由は baseline の側で、
素のモデルは選択肢の列挙と解説を返すため、**成果物でない散文まで成果物として数えてしまう**。
実例では単発測定で 80-94% 削減と出たものが、実セッション再測では
「over-build の余地がある機能で 60-94%、既に最小のコードでは wash」に落ちた。

正しい測り方は、**素のエージェント (介入なしで普通に仕事をする状態) を baseline にして、実セッションで測る**こと。
併せて有効だった設計:

- 測る指標と**落とす門を分ける** — 行数は記録のみ、別に correctness gate を置く。
  さもないと「短いが壊れている」出力が最高スコアを取る
- 構造チェックだけで実行していない項目は、その旨を明記する (何を検証していないかを曖昧にしない)
- テストの追加は bloat ではなく**正の信号**として別扱いにする
- 安全性の要求は**タスク文から意図的に省く** (実際のチケットと同じ条件にし、安全確認を忘れる介入を検出する)

報告作法として、自分の見出し数値が反駁されたら撤回して下げ、自分に不利な第三者測定も併記する。
監査基準として数値を引くときは、出所が撤回済みでないか確認する (SKILL.md の「使った版の SHA を記録する」と同じ趣旨)。

出所: `DietrichGebert/ponytail` の `benchmarks/README.md` (honesty note) と `benchmarks/agentic/README.md` (単発と実セッションの設計比較表)

## 出所メモ: ponytail を蒸留版にしなかった判断

上記 4 項目は `DietrichGebert/ponytail` (2026-08-04 時点 HEAD `16f29800fd2681bdf24f3eb4ccffe38be3baec6b`) から採録した。
**同リポジトリの蒸留版と原典 clone は意図的に作っていない。** 理由:

- 主要な価値が既存の蒸留版と被る — 効果測定の方法論は `claude-cookbooks` (grader 固定・ハーネス設定差の測定) が公式かつ上位互換、
  1 spec を N 形式へ投影したときの drift 検出は `claude-code-hooks` の 5 段階検査 (exists / presence-check / content-match / field-level / cross-file) が上位互換、
  `SubagentStart` と Windows 差分も `claude-code-hooks` に既収載、description の負トリガは `skills` (anthropics/skills) の TRIGGER/SKIP 実例が手本
- 非重複は上記 4 項目とホスト能力マップ (instruction-tier / plugin-tier、20 以上のホスト) のみ。後者は他エージェントの話で、
  かつホスト能力は月単位で変わるため最も腐りやすい
- 継続追従のコストが見合わない — 単独メンテナ主体で、commit cadence が週 70 → 1 まで落ちて 2026-07-15 以降停止。
  同一ルール文の近似コピーが 20 本以上あり信号密度も低い
- 探索索引 (`references/awesome-harness-engineering.md` の Skills & MCP 欄) に既収載で、存在を知る用途はそれで足りる

再検討の条件: 開発が再開してホスト能力マップが継続更新されるようになった場合、または上記の被りが解消した場合。
